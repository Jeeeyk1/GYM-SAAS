1. The Onboarding Flow
What you described:

I create the gym → email goes to the owner → owner clicks a link → fills out their account → logs in as GYM_OWNER

Good news: the backend mechanic is already correct. The invite token system does exactly this. The gap is just two things:

No email service — right now the inviteToken is returned in the API response body (useful for testing/Postman, bad for production). We need a real email send: something like https://app.gymsaas.com/activate?token=xxx landing in the owner's inbox.

The activation "form" is a frontend page — the web app (Next.js) needs an /activate route that takes the token from the URL, shows a "set your password" form, and calls POST /auth/accept-invite. That's purely a web task.

What the actual onboarding would look like with email:


Platform admin fills form on web → POST /admin/gyms
  → Server creates gym + owner staff record
  → Server sends email to ownerEmail: "Click here to activate your gym"
  → Owner clicks link → lands on /activate?token=xxx
  → Fills out password → POST /auth/accept-invite
  → Redirected to gym dashboard, logged in as GYM_OWNER
The token flow is solid. We just need an email provider plugged in.

2. "Not enough information" on gym creation
Currently POST /admin/gyms only takes slug, name, ownerEmail, plan. You're right that this is thin. A real onboarding probably needs:

ownerFirstName, ownerLastName (so the welcome email is personalized and the staff record is meaningful)
address, phone for the gym profile
timezone (critical for check-in time display, operating hours, auto-checkout logic)
Maybe a plan selection UI
Some of this goes on client_profiles (which already has address, phone, timezone, etc.) — we're just not collecting it at creation time. The architecture supports it, we just need to expand the CreateGymDto to optionally accept profile fields and populate them during the transaction.

3. RBAC — Do We Have It?
Partially. Here's the honest state:

Level	Status
Platform admin guard (PLATFORM_ADMIN)	✅ Works — /admin/* is protected
Gym-level role guard	⚠️ The guard class exists but no endpoints use it
Staff scoped to their gym	✅ Data-level (client_id filter) but no HTTP-level enforcement
Member can only see their own data	❌ Not enforced yet
Right now any valid JWT + correct x-gym-slug can hit any endpoint. A front_desk staff member has the same API access as the gym_owner. That's a gap. We need to decorate endpoints with role requirements, something like:


GET /members       → GYM_OWNER, GYM_ADMIN, FRONT_DESK (read)
POST /members      → GYM_OWNER, GYM_ADMIN
PATCH /members/:id → GYM_OWNER, GYM_ADMIN
POST /checkins     → FRONT_DESK, GYM_ADMIN, GYM_OWNER (or MEMBER for self-scan)
GET /checkins/active-members → all staff roles
This is Phase 1.4 or 1.5 territory — it's a cross-cutting concern that touches every controller.

4. The Check-in Scenarios — You've Got It Right
What you described maps perfectly to what's built:

Scenario	What member does	What staff does	Method in API
Gym scans member's QR	Shows QR on mobile app	Scans with kiosk/tablet	qr_staff_scan + qrToken
Member scans gym QR poster	Opens mobile app, scans wall QR	Nothing	qr_self_scan (member's JWT auto-identifies them)
Manual	—	Looks up member by name/number	manual + memberId
The only thing worth clarifying: for "member scans gym QR and gets checked in automatically" — this requires the member to be in the mobile app and logged in. The app reads the QR payload { type: "gym_checkin", slug: "..." }, then calls POST /checkins with method: qr_self_scan using their auth token. It's seamless from the member's perspective but the app must be the bridge. You can't do a "scan with phone camera → automatically checked in" without an app intercepting the QR.

5. What I'd Suggest We Tackle (In Order)
Given what you want, here's a clean roadmap:

Phase 1.4 — Email + RBAC (these are tightly related)

Add an email service (I'd suggest Resend — simple API, good free tier, works well with NestJS)
Expand CreateGymDto with owner name + profile fields
Wire up gym-level RBAC guards on all existing controllers
Add POST /staff endpoint (staff creation with invite email)
Phase 1.5 — Feature Overrides

GET/PATCH /features so the gym owner can toggle features and configure them (loyalty points per checkin, welcome message template, etc.)
This is also what gates checkin.active_members_board
Phase 1.6 — Web App (Next.js)

Gym activation page (/activate?token=xxx)
Gym owner dashboard
Members list / check-in history
Staff management
Phase 1.7 — Mobile App

Member login
QR scanner (self-scan)
Personal check-in history
The One Architectural Decision to Make Now
Email provider. The invite system is built assuming you'll plug one in. Options:

Resend — cleanest API, React Email templates, generous free tier
SendGrid — industry standard, more complex
SMTP (nodemailer) — self-hosted, good for dev/staging
Which direction do you want to go? Once that's decided, the email integration is a small contained module (EmailModule) that AuthModule and AdminModule inject. Everything else flows from there.
