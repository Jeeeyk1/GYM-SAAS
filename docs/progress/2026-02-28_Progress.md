What's Missing (the actual work)
1. Members controller + QR token generation
The CheckInRequest accepts a qrToken but there's no endpoint to generate one yet. Members need a QR token to scan in. This is probably a prerequisite.

2. CheckinsModule — the core work
checkins.module.ts
checkins.controller.ts — POST /checkins (the check-in action)
checkins.service.ts — orchestrates the flow
dto/create-checkin.dto.ts
3. Feature Resolver Service
The check-in service needs to call deepMerge(feature_definitions.default_config, override.config) to get runtime config per gym. This is referenced in CLAUDE.md as Phase 1.4 but check-ins depend on it — the behavior handlers need to know each gym's config.

4. Behavior Registry + Handlers (the interesting part)
CLAUDE.md is explicit: new behaviors = new handler class, not if/else. The pattern is:


CheckInBehaviorRegistry
  ├── LoyaltyPointsHandler     (checkin.loyalty_points feature)
  ├── WelcomeMessageHandler    (checkin.welcome_message feature)
  └── ActiveMembersBoardHandler (checkin.active_members_board feature)
Each handler runs after a check-in is recorded, produces a CheckInOutcome, and the outcomes array gets stored in metadata and returned in the response.

The Full Flow (as I see it)

POST /checkins
  │
  ├── 1. Resolve tenant (x-gym-slug → clientId) — already works
  ├── 2. Authenticate request (JWT guard)
  ├── 3. Validate: is checkin.basic enabled for this gym?
  ├── 4. Resolve member: from qrToken OR memberId (staff manual entry)
  ├── 5. Duplicate check: was this member already checked in within X minutes?
  ├── 6. INSERT into check_ins
  ├── 7. Run behavior registry → collect outcomes[]
  ├── 8. UPDATE check_in.metadata with outcomes
  └── 9. Return CheckInResponse
